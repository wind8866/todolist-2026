**这些文档通常分别由谁写**
中小型项目里，一个人常兼多角，但职责逻辑通常不变。

- 项目经理：写项目计划、里程碑、风险、资源、沟通机制、上线协调、结项材料。
- 产品经理/BA：写需求文档、流程、原型、功能说明、变更说明，是需求口径的第一责任人。
- 架构师/技术负责人：写总体方案、技术架构、模块边界、关键技术决策、非功能方案。
- UI/UX设计师：写交互说明和视觉设计规范。
- 开发工程师/开发负责人：写详细设计、接口文档、配置说明、自测记录、联调说明。
- 测试工程师/测试负责人：写测试计划、用例、缺陷报告、测试报告、回归结论。
- 运维/DevOps：写部署手册、上线方案、监控告警、备份恢复、应急回滚方案。
- DBA/安全角色：在有条件时补充数据库设计评审、安全基线、审计要求。

**按“完整功能分期”的开发流程**
这类项目不是按两周冲刺，而是按“一个可独立验收的完整功能包”来切期。每一期通常按下面流程推进。

1. 项目启动  
明确业务目标、预算、范围边界、参与角色、交付方式。  
此时核心产出是立项书、项目章程、初步范围、初步排期。

2. 总体规划与分期  
把整个项目拆成若干“完整功能期”，每一期都应具备相对独立的业务闭环。  
例如：`一期做基础账号、组织、权限、核心主流程`，`二期做统计报表、消息通知、移动端支持`。  
此时核心产出是总体路线图、分期范围说明、总里程碑计划。

3. 本期需求分析与确认  
只分析当前这一期，不把未来所有细节一次写死。  
产品经理组织业务调研，沉淀业务流程、页面原型、字段规则、状态流转、权限规则、接口需求，并与业务方确认，形成“本期需求基线”。  
这个环节最关键的管理动作不是“多写文档”，而是“冻结边界”。冻结后新增需求默认进入下一期，除非走正式变更。

4. 方案设计  
技术负责人根据本期需求，输出总体技术方案和详细设计。  
重点包括：模块拆分、数据模型、接口协议、部署方式、日志监控、权限方案、异常处理、回滚思路。  
中小型项目里，很多团队会把“总体设计 + 详细设计 + 接口文档”合并成一份，完全可以，但内容不能丢。

5. 开发与联调  
项目经理按模块排开发任务，开发按设计实现，进行代码评审、自测、联调。  
这个阶段常见文档较轻，更多是任务单、接口文档、自测记录、配置说明、联调清单。

6. 测试与业务验收  
测试根据需求文档和设计文档编测试用例，执行功能、回归、性能、安全等测试。  
业务方通常会参与 UAT 验收，确认“本期范围是否达到预期”。  
若发现缺陷，区分为：必须本期修复的问题、可接受的问题、纳入下一期优化的问题。

7. 上线发布  
上线前需要有明确的发布窗口、操作步骤、负责人、回滚方案、数据备份和验证清单。  
上线不应只靠口头沟通。即便是中小型项目，也建议保留一份正式的上线方案和上线确认记录。

8. 运行支持  
上线后进入观察期和维护期，处理用户反馈、生产问题、性能瓶颈、监控告警。  
这里会持续形成问题台账、运维记录、版本发布记录。

9. 下一期立项  
把线上反馈和未纳入本期的需求沉淀进需求池，再做下一完整功能期的范围确认。  
注意这里不是“随来随做”，而是再走一次“需求确认 → 设计 → 开发 → 测试 → 上线”的完整闭环。

| T8 | 发布上线 | 发布说明 | 可访问版本 | 1h | 冒烟通过 |

这份文档的作用不是“排期看起来专业”，而是避免你开发中随意切题。它会强迫你按功能闭环推进。

4. 测试与验收清单
你不需要写完整测试计划，也不需要模拟测试团队写一大堆标准化文档。对这个项目来说，一份场景化清单就够了。它的职责只有一个：验证你的实现是否符合 PRD 和技术设计。

最省力的写法是：

| 编号 | 场景 | 操作步骤 | 预期结果 |
|---|---|---|---|
| C1 | 首次打开无数据 | 清空 localStorage 后打开页面 | 显示“请添加任务” |
| C2 | 新增任务成功 | 输入合法标题后保存 | 任务出现在最前 |
| C3 | 标题为空校验 | 不输入标题直接保存 | 阻止保存并提示 |
| C4 | 编辑任务 | 修改标题后保存 | 列表和存储同步更新 |
| C5 | 标记完成 | 点击复选框 | 状态变更，样式变化，`completedAt` 写入 |
| C6 | 搜索过滤 | 输入关键字 | 实时显示匹配结果 |
| C7 | 默认视图拖拽 | 在仅显示未完成状态下拖拽 | 完整列表顺序符合规则 |
| C8 | 刷新恢复 | 执行多次增删改后刷新 | 数据和顺序不丢失 |

你会发现，验收清单其实不是“测试人员额外加工作”，而是你用来检查自己有没有漏规则的工具。你之前漏掉 `sortOrder` 方向，就是因为没有把“排序恢复”和“新增插前”做成验收项。

**非必要文档**
这些你知道作用就够了，没必要现在专门写：

- BRD / 商业需求文档：说明商业价值和收益，中小个人项目通常可以省略。
- 项目章程 / 立项书：适合正式团队管理，对你这个项目价值不大。
- 单独 UI 规范文档：如果界面不复杂，可直接并入 PRD 或设计稿注释。
- 独立接口文档：纯前端 localStorage 项目一般不需要；将来有后端再补。
- 独立数据库设计文档：现在可以并入技术设计。
- 风险台账：中小项目可在技术设计里用“风险与待定项”代替。
- 会议纪要 / 周报：单人项目没必要。
- UAT 报告：测试清单通过后，一句话记录结论即可。
- 复盘报告：不是必须，但每期结束后写半页“做得好/做得差/下期改什么”很有帮助。

**最省力的写法**
你现在最适合的不是“按角色写文档”，而是“按交接点写文档”：

1. 产品交接给开发：PRD  
2. 开发交接给自己实现：技术设计  
3. 项目经理交接给执行：任务拆解  
4. 测试交接给上线：验收清单  
5. 运维接住上线：发布说明
